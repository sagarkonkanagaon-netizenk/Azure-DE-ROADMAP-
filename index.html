``` – SQL: Top 3 earners per dept (asked at Deloitte, Accenture, Tiger Analytics) SELECT * FROM ( SELECT emp_name, dept, salary, DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk FROM employees ) x WHERE rnk <= 3; – LTE (Last Time Entry) Logic — critical pattern for DE interviews SELECT * FROM ( SELECT *, ROW_NUMBER() OVER (PARTITION BY emp_id ORDER BY updated_at DESC) AS rn FROM employee_history ) x WHERE rn = 1; – Recursive CTE: org hierarchy WITH RECURSIVE org AS ( SELECT emp_id, name, manager_id, 0 AS lvl FROM employees WHERE manager_id IS NULL UNION ALL SELECT e.emp_id, e.name, e.manager_id, o.lvl + 1 FROM employees e JOIN org o ON e.manager_id = o.emp_id ) SELECT * FROM org;

🎯 Top Interview Questions — SQL (Your Bank)

Q: How to find nth highest salary? → Use DENSE_RANK or OFFSET-FETCH
Q: Difference between RANK and DENSE_RANK? → RANK skips numbers on ties
Q: Write cumulative sum → SUM() OVER (ORDER BY date ROWS UNBOUNDED PRECEDING)
Q: Find employees earning more than manager → Self-join on manager_id
Q: TRUNCATE vs DELETE → TRUNCATE: DDL, no rollback, resets identity. DELETE: DML, can rollback, supports WHERE
Q: Union vs Union All → Union removes dupes (slower). Union All keeps all rows (faster)

🎯 Top Interview Questions — Spark (Tiger Analytics, Tredence, Deloitte)

Q: Explain lazy evaluation → Transformations build a plan; actions (collect, count, write) execute it. Benefit: optimization, lineage tracking
Q: groupByKey vs reduceByKey → reduceByKey combines locally before shuffle (faster). groupByKey shuffles everything (memory-heavy)
Q: repartition vs coalesce → repartition = full shuffle, can increase/decrease. coalesce = no shuffle, can only decrease
Q: How many jobs/stages/tasks? → 1 Action = 1 Job. Each wide transformation creates a new Stage. Tasks = partitions per stage
Q: What is AQE? → Adaptive Query Execution: dynamically adjusts plan at runtime (skew handling, join strategy)

🔥 Phase 4: PySpark Deep Dive + Delta Lake

PySpark — What to Study

  • SparkSession vs SparkContext — use SparkSession in modern Spark
  • DataFrame API: select, filter, withColumn, alias, cast
  • Joins: inner, left, right, full outer, cross, semi, anti
  • groupBy + agg: sum, count, avg, max, min, collect_list
  • Window functions: RANK, DENSE_RANK, ROW_NUMBER, LAG, LEAD
  • UDFs: register with @udf decorator or udf() function
  • Handling nulls: isNull(), isNotNull(), fillna(), dropna()
  • Handling duplicates: dropDuplicates(subset=[...])
  • Reading: CSV, Parquet, JSON, Delta, JDBC
  • Writing: mode("overwrite"), mode("append"), partitionBy()
  • Streaming basics: readStream, writeStream (Auto Loader)

Delta Lake — What to Study

  • Delta Lake vs Parquet — ACID transactions, time travel, schema enforcement
  • Delta Log (_delta_log) — JSON + checkpoint files tracking all operations
  • MERGE INTO — upsert logic (insert if new, update if changed)
  • Time Travel: VERSION AS OF / TIMESTAMP AS OF
  • Schema enforcement vs schema evolution (mergeSchema option)
  • Z-Ordering: collocate related data, improves file skipping
  • OPTIMIZE — compact small files into larger ones
  • VACUUM — delete old files (default 7-day retention)
  • SCD Type 1: overwrite with MERGE
  • SCD Type 2: add effective_date, end_date, is_current flag
  • Incremental load without updated_at → Row Hash comparison
```
``` # MERGE INTO — the single most important PySpark interview pattern from delta.tables import DeltaTable delta_tbl = DeltaTable.forPath(spark, ”/mnt/silver/employees”) delta_tbl.alias(“target”).merge( source_df.alias(“source”), “target.emp_id = source.emp_id” ).whenMatchedUpdate(set={ “salary”: “source.salary”, “updated_at”: “source.updated_at” }).whenNotMatchedInsert(values={ “emp_id”: “source.emp_id”, “salary”: “source.salary”, “created_at”: “source.updated_at” }).execute() # SCD Type 2 — track history from pyspark.sql.functions import current_date, lit, sha2, concat_ws # Generate row hash to detect changes (when no updated_at column) df_hash = df.withColumn(“row_hash”, sha2(concat_ws(”||”, df.name, df.salary, df.dept), 256)) # Z-Ordering + OPTIMIZE spark.sql(“OPTIMIZE silver.employees ZORDER BY (dept, emp_id)”) spark.sql(“VACUUM silver.employees RETAIN 168 HOURS”) # Time Travel df_v1 = spark.read.format(“delta”).option(“versionAsOf”, 1).load(”/mnt/silver/emp”)

🎯 PySpark + Delta Lake Questions (All Companies in Your Bank)

Q: Delta Lake vs Parquet? → Delta adds: ACID transactions, time travel, schema enforcement, MERGE support, optimized file layout
Q: Incremental load without updated_at? → Row Hash: SHA2 all columns, compare hash in source vs target, merge on key + hash mismatch
Q: What is Delta Log? → _delta_log folder with JSON transaction logs; every write creates a new log entry; checkpoint every 10 commits
Q: Z-ordering benefit? → Co-locates related data in same files; Spark can skip entire files during reads using data skipping stats
Q: VACUUM purpose? → Removes files no longer referenced by Delta table; default 7-day retention to support time travel
Q: How to handle null values? → df.fillna(0, subset=['salary']), df.dropna(how='all'), df.where(col('id').isNotNull())

"For incremental loads I use MERGE INTO on Delta tables. For SCD Type 2, I add effective_start_date, effective_end_date and is_current columns, closing the previous record on update. I also run OPTIMIZE with Z-ORDERING on high-cardinality filter columns to improve read performance."

🏗️ Phase 5: Medallion Architecture + Data Modeling

Medallion Architecture — Layer by Layer

  • Landing Zone: Files dropped by source, no processing
  • Bronze (Raw): Ingest as-is, add audit columns (ingestion_ts, source_file, batch_id). No transformations. Use Auto Loader for streaming
  • Silver (Cleaned): Remove nulls, dedup, standardize formats, type casting, apply business rules, join lookups. Store as Delta
  • Gold (Curated): Aggregated, business-ready views or tables. Fact + Dimension model. Optimized for BI/reporting
  • Audit columns: created_at, updated_at, batch_id, source_file, is_active, row_hash
  • Auto Loader: cloudFiles format — auto-detects new files in ADLS, processes incrementally
  • CDC (Change Data Capture): Track inserts/updates/deletes from source

Data Modeling — What to Study

  • Star Schema: Fact table + Dimension tables (denormalized)
  • Snowflake Schema: normalized dimensions (sub-dimensions)
  • 3NF: Fully normalized, OLTP use case
  • Fact table: contains measures + FK to dims (sales_amount, qty)
  • Dimension table: descriptive attributes (customer, product, date)
  • Surrogate keys: system-generated IDs independent of source
  • SCD Type 1: overwrite — no history
  • SCD Type 2: add row with new version — full history
  • Data Lakehouse = Data Lake + ACID + query capability (Delta)
  • Data Mesh: domain-owned data products (Accenture loves this)
  • Data Vault: hub, satellite, link tables (highly scalable)
```

```

🎯 Architecture Questions (EY, Deloitte, Infosys, Cognizant)

Q: Explain Medallion Architecture → Bronze: raw + audit columns. Silver: cleaned + business rules. Gold: aggregated for BI. Each layer is Delta
Q: Fact vs Dimension tables? → Fact: numeric measures + FK (sales, qty). Dimension: descriptive context (customer name, date)
Q: Star vs Snowflake schema? → Star: faster queries, denormalized dims. Snowflake: less storage, normalized dims, more joins needed
Q: What is a Data Lakehouse? → Combines data lake (cheap storage, any format) with data warehouse (ACID, schema, SQL) — enabled by Delta Lake
Q: How to implement SCD Type 2? → New record with effective_start_date, NULL effective_end_date, is_current=True; update old record's end_date and is_current=False

⚡ PySpark — Core Concepts (Most Asked)
  • Lazy Evaluation: Transformations (filter, select, join) just build a logical plan. No execution until an action (collect, count, write, show) is called. Benefit: Spark can optimize the whole plan before running.
  • groupByKey vs reduceByKey: reduceByKey combines values locally on each partition before shuffling (map-side reduce). groupByKey sends all values to the reducer first — more data over network, higher memory usage. Always prefer reduceByKey for aggregations.
  • repartition vs coalesce: repartition = full shuffle, can increase OR decrease partitions. coalesce = no shuffle, can ONLY decrease. Use coalesce before writing to reduce output files.
  • Broadcast join: Copies small table (<10MB by default) to every executor. Eliminates shuffle on the large table side. Use broadcast() hint or set spark.sql.autoBroadcastJoinThreshold.
  • UDF registration: @udf(returnType=StringType()) decorator or udf(lambda x: x.upper(), StringType()). UDFs break Catalyst optimization — use built-in functions first, UDFs as last resort.
  • Jobs/Stages/Tasks: 1 Action = 1 Job. Each wide transformation (groupBy, join, sort) creates a new Stage boundary. Tasks = number of partitions in that stage.
  • AQE (Adaptive Query Execution): Dynamically adjusts query plan at runtime — coalesces small partitions, changes join strategy, handles data skew automatically. Enabled by default in Databricks.
  • Incremental load without updated_at: Compute SHA2 hash of all business columns. On merge: insert if key not in target. Update if key exists but hash changed. No hash change = no update needed.
  • Data Skew handling: Salting — add random salt key to skewed partition key, repartition, process, then aggregate. AQE handles it automatically in Databricks.
  • Streaming vs Batch: Batch = bounded data set processed at intervals. Streaming = unbounded, continuous processing with micro-batches (Spark Structured Streaming). Use streaming for <5-minute latency requirements.
🗄️ SQL — Coding & Concepts (All Rounds)
  • nth highest salary: SELECT DISTINCT salary FROM emp ORDER BY salary DESC LIMIT 1 OFFSET (n-1) — OR use DENSE_RANK() = n
  • Top 3 per department: DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) and filter rank <= 3
  • Cumulative sum: SUM(salary) OVER (PARTITION BY dept ORDER BY hire_date ROWS UNBOUNDED PRECEDING)
  • Employees earning more than manager: Self join — e1 JOIN e1 as mgr ON e1.manager_id = mgr.emp_id WHERE e1.salary > mgr.salary
  • Find gaps in sequence: Use LAG() to find where current_id - prev_id > 1
  • TRUNCATE vs DELETE: TRUNCATE = DDL, no WHERE, no rollback, resets identity, faster. DELETE = DML, supports WHERE, can rollback, triggers fire.
  • Stored proc vs function: Function must return a value, cannot modify DB state, can be used in SELECT. Stored proc can return multiple result sets, can modify data, cannot be used in SELECT.
  • Union vs Union All: Union removes duplicates (sorts data = slower). Union All keeps all rows including dupes (faster). Use Union All unless you specifically need deduplication.
  • Star vs Snowflake schema: Star = denormalized dims, faster queries, more storage. Snowflake = normalized dims, less storage, more joins needed. Choose Star for BI/reporting, Snowflake for strict normalization requirements.
  • Pivot row to column: CASE WHEN + GROUP BY pattern or SQL Server PIVOT syntax
🔷 Azure Data Factory — Pipeline Patterns
  • Incremental load pattern: 1) Lookup last watermark from control table. 2) Query source WHERE updated_at > watermark. 3) Copy to target. 4) Update watermark table with new max(updated_at).
  • Metadata-driven pipeline: Store source/target mappings in a config table. ForEach activity reads config table via Lookup. Inside ForEach: Copy activity with dynamic source/sink parameters.
  • Integration Runtime types: Azure IR (cloud-to-cloud, no config needed). Self-Hosted IR (for on-prem or private network access — install on a VM). Azure-SSIS IR (for running SSIS packages in cloud).
  • Copy 3TB from on-prem: Self-Hosted IR + binary copy (no parsing = maximum throughput). Set parallelCopies higher. Use staging in Azure Blob. Schedule during off-peak. Can split into chunks using file-based partitioning.
  • Error handling: On Failure dependency path → send to error folder. Retry policy: set retryCount and retryIntervalInSeconds per activity. Log error to Log Analytics. Email via Logic App trigger on failure.
  • Schema drift in ADF Data Flows: Enable "Allow schema drift" on source. Use schemaModification:allowInsertAndUpdate in sink. Dynamic column mappings using patterns.
  • Key Vault integration: Create Azure Key Vault. Store secrets. In ADF, create AKV Linked Service. Reference secret using @{linkedService().secretName} in linked service definition.
  • Trigger types: Schedule (cron), Tumbling Window (fixed-size windows with dependency support), Event-based (fires on blob creation/deletion), Manual (on-demand).
  • Pass parameters to Databricks: In Notebook Activity → Base Parameters field → pass JSON key-value pairs. In notebook, receive with dbutils.widgets.get("param_name").
🏭 Databricks — Platform & Architecture
  • Job cluster vs Interactive cluster: Interactive = long-running, for development/notebooks, shared by multiple users. Job cluster = spun up for a specific job, terminates after, cheaper, isolated, for production workloads.
  • Unity Catalog: 3-level namespace: catalog.schema.table. Centralized governance across all Databricks workspaces. Row/column-level security. Data lineage. Shares data across workspaces without copying.
  • %run vs dbutils.notebook.run(): %run = inline execution in same session (shares variables, same cluster). dbutils.notebook.run() = separate session, returns a string result, supports timeout and parameters.
  • Delta Log: _delta_log/ folder contains JSON files for each transaction and checkpoint files every 10 commits. Enables time travel, ACID, schema evolution, audit history.
  • Caching vs Persisting: cache() = shorthand for persist(StorageLevel.MEMORY_ONLY). persist() lets you specify storage level: MEMORY_ONLY, MEMORY_AND_DISK, DISK_ONLY. Use MEMORY_AND_DISK for large datasets that don't fit in memory.
  • Autoscaling clusters: Cluster scales between min and max workers based on pending tasks. Good for variable workloads. Be careful — scaling up takes ~2 min; don't use for time-critical streaming jobs.
  • Delta Live Tables (DLT): Declarative pipeline framework. Define tables with @dlt.table decorator. Handles dependencies, error handling, monitoring automatically. Good for continuous pipelines.
  • Optimization techniques: File compaction with OPTIMIZE. Data co-location with Z-ORDER. Remove stale files with VACUUM. Caching hot datasets. Broadcast small lookup tables. Partition by date columns for time-based queries.
💾 Delta Lake — Advanced Patterns
  • Delta Lake vs Parquet: Parquet = columnar file format, no ACID. Delta = file format + transaction log + ACID + time travel + schema enforcement + MERGE support + streaming + batch unification.
  • MERGE INTO: ACID upsert — insert new records, update changed records, optionally delete removed records. Single atomic operation. Based on matched/not-matched conditions.
  • Time Travel: SELECT * FROM table VERSION AS OF 5 — reads table state at version 5. SELECT * FROM table TIMESTAMP AS OF '2024-01-01' — reads state at that timestamp. Used for auditing and debugging.
  • Schema evolution: By default, Delta enforces schema on write (rejects extra columns). Enable schema evolution: .option("mergeSchema", "true") on write, or ALTER TABLE ADD COLUMN.
  • Z-Ordering: Co-locates related data within same data files. Run: OPTIMIZE table ZORDER BY (column). Benefits: file skipping during reads on those columns. Best for high-cardinality columns frequently used in WHERE clauses.
  • OPTIMIZE: Compacts many small files into larger ones (default target: 1GB). Improves read performance. Run periodically, not after every write.
  • VACUUM: Physically deletes files no longer referenced by Delta table. Default retention: 7 days (168 hours). Running VACUUM removes ability to time-travel to versions older than retention period.
  • SCD Type 2 in Delta: On each batch, find changed records (key exists + hash different). Update target: set end_date = today, is_current = False. Insert new version: start_date = today, end_date = NULL, is_current = True.
🔧 General Azure + Cloud Architecture
  • ADF vs Logic Apps vs Azure Functions: ADF = orchestrate large-scale data pipelines. Logic Apps = workflow automation, system integrations (connectors-based). Azure Functions = lightweight event-driven serverless code (HTTP trigger, timer, event hub).
  • Synapse vs Databricks: Synapse = integrated analytics + SQL Data Warehouse + limited Spark. Databricks = best-in-class Spark, ML/AI, Delta Lake native. Use Databricks for complex ETL/ML; Synapse for SQL-heavy analytics workloads.
  • ETL vs ELT: ETL = transform before loading (traditional, limited by tool). ELT = load raw first, transform in cloud using native compute (modern, scalable). Azure pattern is ELT: load to ADLS, transform with Databricks.
  • Dedicated SQL Pool vs Serverless: Dedicated = provisioned compute/storage, pay always, for high-throughput consistent workloads. Serverless = on-demand, pay per TB scanned, good for ad-hoc queries on ADLS.
  • Data Lineage: Track data from source to destination — which tables fed which, what transformations applied. Azure Purview provides automated lineage from ADF pipelines and Databricks.
  • Real-time pipeline: Source → Azure Event Hubs → Stream Analytics / Databricks Structured Streaming → Delta Lake / Power BI streaming dataset. (PROJECT_3 pattern)
  • PolyBase: Synapse Analytics feature to query external data in ADLS/Blob directly without loading. Creates external tables that point to files. Used in PROJECT_16.
  • High availability for Azure SQL: Geo-replication (readable secondary in another region). Auto-failover groups. Zone-redundant deployment. Point-in-time restore (up to 35 days).
🐍 Python — Coding Questions from Your Bank
  • Palindrome check: s == s[::-1] — or use two-pointer approach
  • Word count in string: from collections import Counter; Counter(s.split())
  • Prime numbers up to N: Sieve of Eratosthenes — create boolean array, mark multiples as non-prime
  • Fibonacci sequence: Generator pattern: a, b = 0, 1; while True: yield a; a, b = b, a+b
  • Split name into first/last: df['first'] = df['full_name'].str.split(' ').str[0]; df['last'] = df['full_name'].str.split(' ').str[-1]
  • Find duplicates in list: [x for x, count in Counter(lst).items() if count > 1]
  • Consecutive appearances: Group consecutive equal elements using itertools.groupby, filter groups with len >= n
  • List vs Tuple vs Set: List = ordered, mutable, allows dupes. Tuple = ordered, immutable, allows dupes (use for fixed data). Set = unordered, mutable, no dupes (use for membership testing)
  • Replace vowels: re.sub('[aeiouAEIOU]', ' ', string) — or loop with str.maketrans
  • Parse JSON to DataFrame: import json; data = json.load(f); pd.DataFrame(data) — handle nested JSON with pd.json_normalize()
  • Merge two dicts: {**dict1, **dict2} — or dict1 | dict2 (Python 3.9+)
  • Connect to DB with Python: import pyodbc; conn = pyodbc.connect('DRIVER={SQL Server};SERVER=...;DATABASE=...;UID=...;PWD=...'); pd.read_sql(query, conn)
